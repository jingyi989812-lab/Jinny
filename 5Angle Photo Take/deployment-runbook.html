UR Klinik · Photo Flow

Deployment Runbook

Standing up the photo gateway on the Windows Server so that treatment photos land in the right Synology customer folder automatically — without a therapist ever opening Synology.

Host: Windows Server + IIS Storage: Synology DS225+ Devices: iPhone 6 · iOS 12 Time: ~90 minutes
The shape of it

What you are building

The Windows Server hosts everything the therapist touches. The Synology goes back to being what it is good at — a file store. Nothing needs to be installed on the NAS at all.

Clinic iPhone
Photo Flow app
Sends customer ID, phase, angle and the image over HTTPS. Never sends a path.
→
Windows Server
IIS + Node gateway
Validates, derives the destination, writes over SMB. Holds the NAS credential.
→
Synology DS225+
Shared folder
Folders appear on demand. Synology Drive indexes them as usual.
The rule everything else protects

The phone never sends a folder path. It sends customerId, phase and angle, and the gateway derives \\NAS\UR-Klinik-Photos\RU-2756\2026-09-10\BEFORE\1-FRONT.jpg. That is both the security boundary — a client that names its own path can write anywhere via ..\..\ — and the product promise, enforced structurally instead of by good behaviour in the UI.

Part 1

Prepare the Synology share

Do this first: the Windows Server has nowhere to write until it exists.

  1. Create the shared folder

    Control Panel → Shared Folder → Create — name it UR-Klinik-Photos. Enable data checksum for advanced integrity. Leave the recycle bin on; it is a cheap safety net for a deleted customer folder.

  2. Create a service account on the NAS

    Control Panel → User & Group → Create — name it svc_photoflow. Give it Read/Write on this one shared folder only, deny everything else, and do not put it in the administrators group.

  3. Turn off 2-factor for that account

    Service accounts and 2FA do not mix — SMB authentication will fail silently. Compensate by keeping the account restricted to the single folder.

  4. Confirm SMB is on

    Control Panel → File Services → SMB. Set the minimum SMB protocol to SMB2 and Large MTU or higher. Do not enable SMB1.

If you use Active Directory

Join the NAS to the domain at Control Panel → Domain/LDAP and grant your existing domain service account rights on the folder instead of creating a local NAS user. Then step 2 of Part 2 becomes unnecessary — the Windows service authenticates with its domain identity directly.

Part 2

Give the Windows Server access

  1. Test the share from the server first

    Log into the Windows Server and open the UNC path in Explorer. Do not continue until a file you create by hand appears in File Station on the NAS.

    # In Explorer's address bar, or PowerShell:
explorer \\SYNOLOGY-NAS\UR-Klinik-Photos
  2. Create a matching Windows account (non-AD sites only)

    Without a domain, SMB pass-through needs a local Windows account whose username and password match the NAS account exactly. Create svc_photoflow on the Windows Server with the same password you set in Part 1.

Two traps that will cost you an afternoon

Do not use a mapped drive letter. A drive like Z: belongs to an interactive login session and does not exist for a Windows service. The service will start cleanly and then fail on every write. Always use the UNC path.

Do not leave the service running as LocalSystem. LocalSystem authenticates to SMB as the computer account, which has no rights on the NAS. The service must run as the account from step 2.

Part 3

Install the gateway

  1. Install Node.js 20 LTS

    Take the Windows x64 MSI from nodejs.org. Accept the defaults; it puts node on the system PATH, which the service installer checks for.

  2. Download NSSM

    Node cannot register itself as a Windows service — it needs a wrapper that speaks the service control protocol. Get nssm.exe from nssm.cc and drop it beside install-service.ps1.

  3. Copy the gateway folder onto the server

    Somewhere permanent, e.g. C:\Apps\photoflow\. Exclude the nas-hosted\ subfolder — that is the fallback for running on the Synology instead and is not used here.

  4. Write the .env file

    Copy .env.example to .env and set both values. Generate a real key — this is what stops anyone on the wifi from writing into customer folders.

    # Generate a key:
powershell -c "[guid]::NewGuid().ToString('N')"

# .env
DATA_DIR=\\SYNOLOGY-NAS\UR-Klinik-Photos
APP_KEY=<the generated key>
PORT=8080
MAX_UPLOAD_MB=12
  5. Install the service

    From an elevated PowerShell in that folder. It will prompt for the service account password.

    cd C:\Apps\photoflow
.\install-service.ps1 -NasShare "\\SYNOLOGY-NAS\UR-Klinik-Photos" `
                      -ServiceAccount ".\svc_photoflow"
Part 4

Prove the write path works

Before touching certificates or phones, confirm the one thing this whole system exists to do. Run this on the server.

# 1. Is it alive?
curl http://localhost:8080/api/health

# 2. Save a photo for a customer whose folder does NOT exist yet.
curl -X POST http://localhost:8080/api/photos ^
  -H "x-photoflow-key: <your APP_KEY>" ^
  -F "customerId=RU-2756" -F "phase=BEFORE" -F "angle=front" ^
  -F "photo=@C:\temp\test.jpg"
What success looks like

You get back {"ok":true,"duplicate":false,"path":"RU-2756/2026-09-10/BEFORE/1-FRONT.jpg"}, and all three folders now exist in File Station — created on demand, by nobody. Run the same command a second time: it returns duplicate: true instead of a second file, which is what makes a retry over bad wifi safe.

Part 5

HTTPS front door

This part is not optional. iOS refuses camera access on plain HTTP, and iOS 12 rejects a self-signed certificate outright — so without a real certificate the therapist simply cannot take a photo.

  1. Enable IIS reverse proxying

    Install the URL Rewrite and Application Request Routing modules, then IIS Manager → server node → Application Request Routing Cache → Server Proxy Settings → Enable proxy.

  2. Create the site

    Point a new IIS site at an empty folder and drop in the supplied iis\web.config. It forwards everything to localhost:8080 and raises the upload limit — IIS caps requests at 30 MB by default, which a batch of iPhone photos will hit.

  3. Get a real certificate

    Use win-acme for a Let's Encrypt certificate on a hostname you control, e.g. photoflow.urklinik.com.my, and point that name at the server's LAN address with split DNS. This is much less painful than an internal CA, which would mean installing a root profile on every iPhone.

  4. Force HTTPS

    Redirect port 80 to 443 so a therapist typing the address bare still lands on a page where the camera works.

Part 6

Lock it down and hand it over

  1. Firewall to the LAN

    Windows Firewall: allow inbound 443 from the clinic subnet only. Block 8080 from everywhere except localhost — the Node service should only ever be reachable through IIS.

  2. Publish the folder in Synology Drive

    Synology Drive Admin Console → Team Folder — enable UR-Klinik-Photos. Files arriving over SMB are indexed normally, so staff see customer folders appear in Drive without anything extra.

  3. Exclude the upload path from antivirus

    Real-time scanning on the spool directory adds latency to every photo and occasionally locks a file mid-write. Exclude C:\Apps\photoflow\.

  4. Set up the phones

    Open the site in Safari, enter the app key once, then Share → Add to Home Screen. On iOS 12 use the app's file-upload capture rather than the live preview — getUserMedia is unreliable on Safari 12 and fails outright in home-screen web apps there.

  5. Back up the index

    _index\customers.json and _audit\ live on the NAS beside the photos, so Hyper Backup covers them with everything else. Confirm the job includes the new shared folder.

Part 7

When something goes wrong

SymptomCause and fix
Service starts, every upload returns 500Almost always SMB rights. Check the service is running as svc_photoflow and not LocalSystem, and that DATA_DIR is a UNC path rather than a drive letter.
401 on every requestAPP_KEY in .env does not match what the phone sends. The service reads .env at install time — re-run the installer after changing it, a restart is not enough.
413 on larger photosIIS request limit. Raise maxAllowedContentLength in web.config, and MAX_UPLOAD_MB to match.
502 from IISNode service is not running, or ARR proxying was never enabled. Check logs\err.log in the app folder.
Camera button does nothing on the iPhoneThe page is not on HTTPS, or the certificate is not trusted by iOS 12. Confirm the padlock in Safari before debugging anything in the app.
Photos land but Drive never shows themThe shared folder is not enabled as a Team Folder, or Drive has not finished its initial index of a folder created after the fact.
Date folder is a day outThe folder name comes from the Windows Server's clock. Check its timezone is Malaysia time — the NAS's own setting is irrelevant here.
Still open

What this runbook does not cover

  • Wiring the app to the API. The prototype still simulates its uploads. The production build needs to POST to /api/photos after each angle passes its quality check — not all ten at the end, which is where clinic wifi will fail you.
  • Where the customer list comes from. Right now the gateway keeps its own customers.json. If bookings live in another system, that becomes the source of truth and the gateway reads from it instead.
  • Offline queue. Photos should sit in IndexedDB with a pending flag and retry with backoff, showing "8 of 10 uploaded" rather than a spinner that lies.
  • Retention and consent. Customer face photos are personal data under the PDPA. Worth settling who may open the Team Folder, and how long photos are kept, before rollout rather than after.
